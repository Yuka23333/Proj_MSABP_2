# CST 工程隔离区

本目录同时容纳两类内容：

- `*.cst`：可独立打开并恢复主要模型数据的 CST 工程容器，纳入 Git；
- 与 `.cst` 同名的目录、`bakN`、缓存和求解结果：由 CST 自动生成，只保留在本机。

## 脚本建模与跨机器迁移：2026-09-24 修正

撤销“命令行或脚本创建的模型不能传输到其他机器”的概括。建模入口是 GUI、Python
还是 VBA，并不能单独决定工程能否迁移；应分别检查历史记录、保存状态、外部依赖和
目标机器上的实际恢复情况。

本次已确认的反例是 `propagate_cylinder_voxel.cst`：

- 本机通过 Python 连接 CST，以 `model3d.add_to_history` 记录旧幻象删除、参数定义、
  材料定义和四层圆柱建模；圆心与各层半径保留参数表达式。
- 保存工程后，将 `.cst` 与同名附属目录一起发送至 `coconutg2`，排除临时目录和锁文件；
  116/116 个文件通过 SHA-256 校验。
- 用户随后确认远端正常恢复。此项是工程迁移成功的证据，尚不等同于真实求解成功，
  也不是“只复制裸 `.cst`”的独立恢复测试。

结构修改优先通过 `model3d.add_to_history` 提交。仅调用
`schematic.execute_vba_code` 执行即时几何操作，不能据此假定已生成可重放的历史记录；
如果宏显式使用 `AddToHistory`，则需按其实际内容判断。参数控制、状态查询等即时操作
与几何历史修改应区分。历史记录完整也不是跨机器迁移的充分条件，仍需核对依赖与恢复。

此前出现过的 Port、Pick 或 Monitor 丢失仍属于具体工程的待定位问题。本次成功尚未
单独隔离“历史记录方式”和“附属目录传输”等因素，不能反推旧故障的唯一根因。

## `msa-bp.cst` 的模板契约

旧版本曾出现裸 `.cst` 副本丢失 Field Monitor、几何 Pick 或依赖 Pick 的 Port 有效引用，
并在求解时报告 `No valid excitation sources defined`。当前维护的 `msa-bp.cst` 已修复：
2026-08-24 在 CST Studio Suite 2025 中将该文件单独复制到空目录后，完成了删除/重画
脚本管理几何、检查 Port 1 与 61 个 Farfield Monitor、真实求解及三条 1D 曲线导出。

Port、Field Monitor、网格和 solver 设置现在属于模板工程。自动化在每次重画后只校验这些
对象，不再通过 Python/VBA 删除、重建或静默修补；模板不完整时应在求解前直接失败。

## 尚未验证的参考工程

以下近期纳入 Git 的 CST 工程目前只作为待整理的参考副本，**尚未完成跨机器 pull 后的
可恢复性验证**：

- `MSA-BP_David_2_body.cst`
- `MSA-BP_David_3_body.cst`
- `MSA-BP_New-Notch_22-10-2013_CST2023.cst`

直接 pull 后，这些工程中的 Port、Pick、Field Monitor、材料引用或其他基础设施可能失效，
不得把“文件可以打开”等同于“模型可以直接求解”。在开发者提交并验证对应的建模准备
与迁移流程（可手动，也可由带历史记录的脚本实现）之前，不应将它们作为无人值守仿真的可靠模板。

`.gitignore` 对本目录采用“默认全部排除、只放行 `*.cst` 和本 README”的策略。因此新增工程时只需把 `.cst` 放在这里；CST 后续生成何种同级工作目录都不会被 Git 收录。

不要把需要长期保存的脚本、配置或人工导出数据放进本目录，因为除 `.cst` 和本 README 外都会被忽略：

- 仿真模板或宏放入 `../templates/`；
- 批量临时算例放入 `../runs/`；
- 求解器导出的数据放入 `../../results/raw/`。
